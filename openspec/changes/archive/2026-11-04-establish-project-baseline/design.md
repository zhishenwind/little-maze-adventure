# Design

## Context

参见 `proposal.md` 的动机。本轮接入前，项目已实现 React Web 游戏并有算法与浏览器测试；本地 `main` 是没有提交的空仓库。首次基线提交 `dec4701` 保存现有可运行实现。用户希望后续修改留下持续记录，当前未提供远程 Git 地址。

## Goals / Non-Goals

**Goals:** 本地可追溯、工具可复现、当前行为可验收、后续协作者能直接按流程开展迭代。

**Non-Goals:** 不引入服务端流程平台，不改变游戏行为，不实现或承诺小程序兼容层，不自动连接远程服务。

## Decisions

1. **沿用现有 Git 仓库并拆分两次提交。** 保留 `main` 和现有用户身份；先保存 Web 基线，再保存流程接入，便于追溯两类变化。无需重建仓库或重写历史。
2. **OpenSpec 为固定版本开发依赖。** 使用 `@fission-ai/openspec@1.16.0` 与 lockfile，避免协作者依赖不同的全局版本。npm 包装脚本使用本项目 CLI，默认关闭遥测，不修改用户全局设置。
3. **使用官方 spec-driven schema 和 core Codex 集成。** 保留上游生成技能原文；在根 `AGENTS.md`、OpenSpec config 和开发文档放项目规则。用户可直接提出本轮实施需求；只有单独调用 propose 的请求才停留在提案阶段。
4. **先补录现有行为，再使用 delta 迭代。** 四项产品能力按真实代码和测试补录，开发流程为本轮新增能力；归档命令同步主规格，使规格与第一份迭代档案自然一致。
5. **统一检查入口，不增加 Git 隐式钩子。** `check` 汇总规格、归档任务、算法与构建，`check:full` 增加浏览器。检查结果写入变更的 verification，保留明确验证依据；不增加每次提交隐式启动浏览器的负担。
6. **轻量维护允许简化。** 无行为变化的错别字和排版修改可直接提交；功能、行为修复和架构变化必须有变更档案。

## Risks / Trade-offs

- 本地仓库不是异地备份 → 明确记录未配置远程；用户给出地址后再接入。
- OpenSpec 校验只验证结构与部分完整性，不证明代码正确 → 保留算法／浏览器测试并在 verification 中对照实际行为。
- 官方技能可能需要重开会话后才发现 → CLI 与根协作规则立即可用，文档同时提供 npm 命令。
- 首条档案包含已实现功能的回填 → 提案、规格及验证记录明确区分既有实现和本轮新增开发能力。

## Migration Plan

执行固定依赖安装与 OpenSpec init，编写项目规则和基线 delta，运行校验及回归测试，确认任务完成后归档同步主规格，再形成流程接入提交。后续只需要 `npm ci` 即可恢复工具。若撤回流程接入，以新的 Git revert 提交恢复，保留历史基线；本轮不执行撤回。
